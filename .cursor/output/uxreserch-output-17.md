## 📋 人間中心設計（HCD）プロセス改善レポート

### 1. 利用状況の把握（Before）
- `npm run dev`（開発サーバー）の計測は、これまでのサイクルで繰り返し「詳細遷移が500ms超」等の指標を検出していたが、これはNext.jsの`--webpack`開発モード特有のオンデマンドコンパイル・SSRオーバーヘッドによるノイズが大きく、実際の本番ユーザー体感を正しく反映していない可能性を検証した。
- `npm run build && npm run start` で本番相当ビルドを起動し、同じ操作フローを計測したところ、`detailNavMs` は111ms、`searchCachedMs` は38msとなり、いずれもこれまで開発モードで問題視していた閾値を大幅に下回った。一方で `topLoadMs`（`networkidle` 到達までの時間）は本番でも4秒超と依然大きく、原因を調査した。
- 原因調査の結果、TOPページ読み込み直後にGTM（Google Tag Manager）の外部スクリプト（`https://www.googletagmanager.com/gtm.js`）が非同期で読み込まれ、Playwrightの `networkidle` 判定（500ms間ネットワークアクティビティが無いこと）がこの外部リクエストの完了待ちに影響されていたことが判明した。実際の描画完了（Web Vitals: `loadEventEnd` は188ms、`firstContentfulPaint` は100ms）は非常に高速であり、GTMスクリプトは `async` 属性付きで読み込まれるため、ユーザーの実体感（描画）をブロックしていないことを確認した。

### 2. ユーザー要求事項
1. **R1**: HCDループの計測ツール（`scripts/hcd-explore.mjs`）が、サードパーティ計測タグの影響を受けずTOP画面の読み込み時間を正しく計測できること。

### 3. 設計による解決策（実装内容）
- 本サイクルでは `src/` 側の実装に問題は見つからなかったため、コードの修正は行わなかった。
- `scripts/hcd-explore.mjs` の `top_load` ステップの待機条件を `waitUntil: "networkidle"` から `waitUntil: "load"` に変更し、GTM等サードパーティスクリプトの完了を待たずに素早く・正確にページ読み込み完了を計測できるようにした。

### 4. 設計の評価結果（After）
- 修正後、同スクリプトで再計測したところ `topLoadMs` は574msとなり、Web Vitalsの実測値（`loadEventEnd`）と整合する妥当な値になった → **R1 合格**。
- 単体テスト148件は変更なくすべて成功。
- 本番ビルドでの検証により、これまで開発モードのノイズにより「遅い」と誤解していた指標（検索・詳細遷移）は実際には問題がないことを確認できた。今後のサイクルでは、疑わしい計測結果が出た場合は本番ビルドでの再検証を優先することとする。
