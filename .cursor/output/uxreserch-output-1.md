## 📋 人間中心設計（HCD）プロセス改善レポート

### 1. 利用状況の把握（Before）
- Playwright で「TOP → 検索 → 夏目漱石 → 詳細 → TOP」をエミュレート
- 検索入力→初回結果表示: **約 3987ms**（目標 500ms を大幅超過）
- `/api/works?q=夏目漱石`: 初回 3.4s / 再取得 1.3–1.7s（全件取得＋JSフィルタがボトルネック）
- 詳細遷移: 約 2.2s
- 検索結果UI自体は正しく表示されるが、待ち時間が長く「固まっている」ように見える

### 2. ユーザー要求事項
1. **R1**: 同一検索クエリの再実行は、結果表示まで **0.5秒以内**
2. **R2**: 検索入力中、結果待ちであることが **即座に** 伝わること
3. **R3**: `/api/works` はキャッシュ可能であること
4. **R4**: 入力中の古い検索リクエストは破棄され、最新クエリの結果だけが表示されること

### 3. 設計による解決策（実装内容）
- SQL 側検索＋カタログ `unstable_cache` を取り込み、`/api/works` のサーバー負荷を削減
- `/api/works` に `Cache-Control: public, s-maxage=300, stale-while-revalidate=3600` を付与（R3）
- `useSearchScreen` にクライアント結果キャッシュ、`AbortController`、debounce 200ms、入力直後の `isLoading` を実装（R1/R2/R4）
- フック／画面の単体テストを追加・更新し、キャッシュヒットとレース条件を検証
- 評価用スクリプト `scripts/hcd-explore.mjs` に同一クエリ再検索の計測を追加

### 4. 設計の評価結果（After）
- 再評価（`node scripts/hcd-explore.mjs`）: Issues **なし** → **合格**
- 検索入力→初回結果: **295ms**（Before 3987ms）
- 同一クエリ再検索（クライアントキャッシュ）: **58ms**（R1: ≤500ms）
- `/api/works` 単体: 初回 ~1.5s → 2回目以降 ~6–7ms（R3）
- 入力直後の `isLoading` / 「検索中」スピナーで待ち状態が即時表示（R2）
- Abort＋最新クエリ判定で古い結果の上書きを防止（R4、テストで確認）
