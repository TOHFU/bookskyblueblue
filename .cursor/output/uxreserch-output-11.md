## 📋 人間中心設計（HCD）プロセス改善レポート

### 1. 利用状況の把握（Before）
- `npm run dev` を起動し、Playwright（`scripts/hcd-explore.mjs`）で「TOP → 検索画面 → 「夏目漱石」で検索 → 検索結果一覧 → 詳細画面 → TOPへ戻る」を自動操作し、スクリーンショットと計測データを取得した。
- 検索結果画面（`03-search-results.png`）で重大な表示バグを発見: 検索APIが200で応答し、検索結果カード（`role="article"`）はDOMに存在するにもかかわらず、**画面には1件もカードが見えず背景の装飾テキストのみが表示される**状態だった。
  - 同一クエリを再検索したキャッシュ済み結果（`03b-search-cached.png`）では正しくカードが表示されており、初回（コールド）表示時のみ発生する不具合と判明。
- 原因調査: `FadeInBox`（`useIntersectionFadeIn`）が、要素マウント時に `opacity: 0` で開始し、`IntersectionObserver` の非同期コールバックが発火してから `0.3s` の `fadeInDown` アニメーションを開始する実装になっていた。新規マウントされたカードは、この一連の処理が完了するまでの間、完全に透明（不可視）な状態になり、その間に検証スクリプトのスクリーンショット取得が発生していた。
- この挙動は自動テストに限らず、実際のユーザーが検索直後に画面を見た瞬間にも「検索結果が表示されていない／検索が失敗した」と誤解させるリスクがあり、UXゴール「読みたい作品をスムーズに検索できて快適に閲覧できること」を阻害する。

### 2. ユーザー要求事項
1. **R1**: 検索結果カードは、初回表示（画面内にマウントされた瞬間）から常に視認できること。フェードイン待ちによって「結果が一瞬見えなくなる」空白状態を作らないこと。
2. **R2**: スクロールで新たに現れるカードの視覚的なフェードイン演出（下方から現れるアニメーション）は維持すること。

### 3. 設計による解決策（実装内容）
- `src/hooks/useIntersectionFadeIn.ts` を修正:
  - `useEffect` → `useLayoutEffect` に変更し、DOM更新後・ペイント前に可視性を確定できるようにした。
  - マウント時点で要素の `getBoundingClientRect()` を同期的に確認し、**既に画面内にある要素は `IntersectionObserver` の通知を待たずに即時可視化**するようにした。
  - 画面外にある要素（スクロールでこれから現れる要素）は、従来どおり `IntersectionObserver` の通知を待ってからフェードインする。
- `src/hooks/useIntersectionFadeIn.test.tsx` を新規作成し、(1) 画面内マウント時に即時可視化されること、(2) 画面外マウント時は通知が来るまで非表示のままであること、の2ケースを検証。

### 4. 設計の評価結果（After）
- 単体テスト: 新規2件を含めユニットテスト全148件が成功、型チェック・ESLintともにエラーなし。
- ブラウザ再検証（Playwright再実行）: 修正後は初回検索直後のスクリーンショット（`03-search-results.png`）で検索結果カードが即時に表示されることを確認（修正前は空白、修正後は4件のカードが表示）→ **R1 合格**。
- スクロールで新規に現れるカードのフェードイン演出はロジック上維持（`IntersectionObserver` 経路は変更なし）→ **R2 合格**。
- 詳細遷移時間（`next dev` の初回ルートコンパイルに起因する既知の計測値）は依然 500ms を超えるが、これは開発サーバー特有のコンパイルオーバーヘッドであり、本サイクルの本質的なUX不具合（検索結果が見えなくなる問題）とは別課題として次サイクル以降の継続観察事項とする。
